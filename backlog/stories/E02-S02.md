## Context

Structural block commands.

## Acceptance criteria

- [x] InsertBlock at parent+index with kind and initial text
- [x] DeleteBlocks removes whole subtrees
- [x] MoveBlocks keeps relative order of the moved set
- [x] Children rules enforced (e.g. no children under heading)
- [x] Tests added; `just check` passes; docs updated if structure changed

## Plan

- `PageCommand` (`InsertBlock`, `DeleteBlocks`, `MoveBlocks`) applied with `PageDoc::apply`, the same pattern as
  the workspace: validate everything first, write, commit once; `Unchanged` when nothing was recorded.
- `InsertBlock { parent, index, kind, text }` mints and returns the `BlockId`. The text container is created
  with `ensure_mergeable_text`, only for kinds that have text; text on a divider is an error.
- `DeleteBlocks { ids }` removes whole subtrees and returns every deleted `BlockId` (parents first). Ids already
  inside another deleted block are fine. An empty list is `Unchanged`.
- `MoveBlocks { ids, new_parent, index }`: the moved set keeps **document order**; blocks inside another moved
  block travel with it. `index` counts the destination's children without the moved blocks. Placed as: first
  block before the sibling at `index` (or after the last), the rest each after the previous one.
- Children rules: no inserting or moving under heading, code, divider, image or unknown blocks; no moving a
  block into itself or its own descendants.
- Tests: each command and rule. A proptest runs random insert/delete/move sequences against a reference model:
  same accept/reject, same structure after every step and after reload.
