## Context

Soft delete via trashed_at; subtree hidden from normal queries.

## Acceptance criteria

- [x] TrashPage hides the subtree from list queries
- [x] Trash query lists trashed roots
- [x] RestorePage restores to the original parent or root if parent is gone
- [x] DeletePagePermanently removes subtree and reports page ids to delete from storage
- [x] Tests added; `just check` passes; docs updated if structure changed

## Plan

Done with E01-S06 on one branch (owner request). New module `workspace/trash.rs`.
- `TrashPage { page, at }` sets `trashed_at` (the caller supplies the time). The page stays in place, so its
  original parent is remembered. "In the trash" means the page or any ancestor has `trashed_at`.
- `root_pages` and `children` skip pages with `trashed_at`, so a trashed subtree disappears from listings.
  New `trash()` lists every page trashed on its own, most recent first.
- `RestorePage { page }` clears `trashed_at`. If an ancestor is still in the trash (the parent is "gone"), it
  also moves the page to the end of the top level, so it doesn't stay invisible.
- `DeletePagePermanently { page }` works only on pages in the trash. It deletes the subtree and returns
  `Outcome::PagesDeleted(ids)` so storage can drop their page docs (E03).
- Rules: no creating or moving into the trash, and a page in the trash can't be moved (restore it first).
  New errors `PageInTrash` and `NotInTrash`. Rename and icon still work in the trash.
- Tests: each command and rule, hidden subtrees, restore when the parent is gone, the deleted-ID list.
