## Context

The owner wants a Notion-style board view: rows grouped into columns by a property, cards dragged between columns to
change that property. And saved views: tabs above a database, each a table or board with its own settings, switched
with a click. Today a database has one table view (ADR-066): its sort and filters live in the `"view"` map and its
hidden columns and widths in each column's schema. Before writing stories, prove a data model on Loro the way E09-S01
did: where views live, how they merge between two devices, how databases saved by this version keep working, how a
card move undoes, and whether grouping 10,000 rows is fast enough. Throwaway-quality tests only; no production code.

## Acceptance criteria

- [x] Spike tests (Loro directly, no production code) show several views per database: tab order, names, layout,
      per-view sort, filters, hidden properties and board grouping
- [x] A database saved by this version opens with its one table view unchanged, and an older peer's edits to it
      still merge with a newer peer's extra views
- [x] Board grouping: one group per option in order plus "No value", cards in row order; a card move changes the cell
      and its place in one undo step
- [x] Two-peer tests: concurrent view creation, view delete vs edit, tab reorder vs delete, the same card moved to two
      groups, a card moved into an option deleted on the other peer
- [x] A view layout from a newer version survives untouched
- [x] Measured: grouping 10,000 rows into a board, and the first screen of each group (release build)
- [x] Proposed ADR with the data model, findings and the open product questions for the owner
- [x] E22 stories written from the findings (status `backlog`)
- [x] Tests added; `just check` passes

## Plan

- `crates/leaf-model/tests/views_spike/` (test target, Loro directly, no production code): `main.rs` holds a `Db`
