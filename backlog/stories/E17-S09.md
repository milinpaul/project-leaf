## Context

Found while fixing E17-S08 (2026-10-30): in a 38,000-character paragraph each arrow key takes about 20 ms and each
word jump up to 60 ms in a debug build, so holding an arrow key lags. Every caret motion in
`leaf-editor/src/caret/motion.rs` segments the whole block from its start into grapheme clusters or words, and a
single arrow press does that four times (snapping the caret, reading it, moving, placing it).

## Acceptance criteria

- [x] Grapheme motions (snap, Left, Right) look only at the text around the caret, with the same results as before
- [x] Word jumps stop scanning once they have their answer and don't collect every word of the block
- [x] A test pins the behaviour on emoji, flags, accents and Devanagari against the old whole-text segmentation, and one keeps an arrow press in a ~38,000-character block quick
- [x] Tests added; `just check` passes; docs updated if structure changed

## Plan

- Measured (debug build, 38,000-character block, caret at 20,000): `snap` and `previous_grapheme` 4.7 ms each,
  `word_left` 3.8 ms; one Left press 18.7 ms, as `caret()`, the selection check, the move and `set_caret` each
  segment the whole block. Reading the text, anchors and the view model cost microseconds.
- `caret/motion.rs`: grapheme motions use `unicode_segmentation::GraphemeCursor` at the caret, which reads only the
  text it needs around it; positions are counted from the caret, not from the start. Word jumps iterate the word
  segments lazily and stop at their answer instead of collecting every word.
- After: one Left press 1.8 ms, a word jump 2.5 ms in a debug build (most of what's left is converting the caret's
  character position to a byte offset, which an optimised build does in microseconds).
- Tests: a property test checks snap, Left, Right and both word jumps against the old whole-text segmentation on
  random text with joined emoji, lone and paired flags, skin tones, combining marks, Devanagari, CJK, numbers with
  points and apostrophes (60,000 cases locally); a speed test (220 presses in a 38,000-character block under 2 s)
  fails on the old code (4.2 s) and passes on the new (0.5 s). No ADR: same behaviour, faster.
