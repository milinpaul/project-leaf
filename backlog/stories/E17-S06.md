## Context

Scrolled to the middle or end of a long page, clicking any block makes the page jump back to the top (a
scroll-up or flicker). Clicking the page title doesn't. The page is a virtual list (`crates/leaf-ui/src/shell/page_list.rs`,
ADR 0035); the title is a header item, blocks are list items.

Likely suspects:
- `PageList::sync` treats the click as "another page" (`page != self.page`, e.g. a `None` page for one frame while
  focus moves) and calls `state.reset`, which starts from the top.
- The click changes many rows (caret or selection data in `BlockRow`), so `changes()` remeasures or splices rows
  above the viewport and the list loses its offset.
- `reveal` / `scroll_to_block` / `pending_scroll` fire with the wrong index on focus.

## Acceptance criteria

- [x] Clicking any block, anywhere in a long page, leaves the scroll position where it was
- [x] Typing, Enter and Backspace in a block mid-page don't move the page except to keep the caret in view
- [ ] Checked on the 10,000-block fixture page (`just fixture`)
- [x] A failing test reproduces the bug before the fix (e.g. in `page_list_window_tests.rs`)
- [x] Tests added; `just check` passes; docs updated if structure changed

## Plan

- Cause: on macOS `handle_view_event` passes every mouse-down to the system input context first, which calls
  `unmarkText`; `Shell::unmark_text` ran `ime_changed`, whose `reveal_caret` scrolled to the *old* caret
  (usually near the top) before the click moved it. The title is its own text field, so it wasn't affected.
- Fix: `unmark_text` only commits a pending draft and never scrolls (`crates/leaf-ui/src/shell/ime.rs`).
- Tests: `page_list_window_tests.rs` — the click-time `unmark_text` call keeps the scroll (failed before: item 796 →
  1), plus clicks after trackpad scrolling on a long and a short page. ADR 0040 notes the rule.
