## Context

The E00-S05 spike found that Loro gives a block a new `TreeID` whenever undo or redo re-creates it (undo of a
delete, redo of a create). BLOCK_MODEL.md assumes `BlockId = TreeID` is stable, which cursor restore on undo and
Phase 1 block links rely on. An ID stored in the block's meta survives every undo/redo cycle (see
`crates/leaf-model/tests/loro_spike.rs`). Decide the block identity scheme before E02-S01 builds on it.

## Acceptance criteria

- [ ] ADR choosing the scheme (likely: a stable `BlockId` in each block's meta, `TreeID` as an internal handle;
      alternatives: soft-delete blocks, or remap IDs on undo)
- [ ] docs/architecture/BLOCK_MODEL.md updated: IDs table, page doc meta, invariant 7 wording
- [ ] Tests added; `just check` passes; docs updated if structure changed
