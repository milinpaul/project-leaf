## Context

The E00-S05 spike found that Loro gives a block a new `TreeID` whenever undo or redo re-creates it (undo of a
delete, redo of a create). BLOCK_MODEL.md assumes `BlockId = TreeID` is stable, which cursor restore on undo and
Phase 1 block links rely on. An ID stored in the block's meta survives every undo/redo cycle (see
`crates/leaf-model/tests/loro_spike.rs`). Decide the block identity scheme before E02-S01 builds on it.

## Acceptance criteria

- [x] ADR choosing the scheme (likely: a stable `BlockId` in each block's meta, `TreeID` as an internal handle;
      alternatives: soft-delete blocks, or remap IDs on undo)
- [x] docs/architecture/BLOCK_MODEL.md updated: IDs table, page doc meta, invariant 7 wording
- [x] Tests added; `just check` passes; docs updated if structure changed

## Plan

Decision only, no model code (E02-S01 builds on it).

- Scheme: each block's meta holds a permanent `id` (UUID v7 string), the same pattern pages already use.
  `BlockId` becomes a UUID newtype in `leaf-core`; `TreeID` stays an internal handle inside `leaf-model`,
  which keeps a `BlockId → TreeID` index and rebuilds it after undo, redo and import.
- ADR-006 with alternatives (soft delete, remapping on undo, our own undo).
- BLOCK_MODEL.md: diagram, IDs table, page doc meta, commands note, invariants (new 8: unique ids; 7 reworded).
- E01-S01 context updated to the new `BlockId`. Proof: the E00-S05 spike tests already show a meta `id`
  survives every undo/redo cycle; `just check` covers the docs.
